# Módulo: Base de datos

## Propósito

Gestiona toda la persistencia del sistema usando SQLite vía `aiosqlite` (async), sin ORM — queries SQL crudas organizadas en funciones por responsabilidad.

## Archivos

| Archivo | Responsabilidad |
|---------|----------------|
| `app/db/sqlite_client.py` | Todas las funciones de acceso a la base de datos |
| `database/schema.sql` | Definición de tablas, índices y constraints |
| `database/init_db.py` | Script de inicialización: crea las tablas si no existen |

**Ruta de la base de datos:** `src/data/phishing_detector.db` (excluida del repo por `.gitignore`)

## Esquema de tablas

### `conversacion`

Una fila por par único sender/cuenta-monitoreada.

| Columna | Tipo | Descripción |
|---------|------|-------------|
| `id_conversacion` | TEXT PK | `sha256(sorted([sender_id, recipient_id]))[:16]` — ID bidireccional |
| `ig_conversation_id` | TEXT | ID nativo de Instagram (si está disponible) |
| `cuenta_monitoreada` | TEXT | `recipient_id` — la cuenta del sistema |
| `participante_id` | TEXT | `sender_id` — ID del remitente |
| `participante_username` | TEXT | Username de Instagram (resuelto en background) |
| `risk_level_actual` | TEXT | Último nivel de riesgo del mensaje individual (LOW/MEDIUM/HIGH) |
| `risk_level_conversacion` | TEXT | Nivel de riesgo holístico (del ConversationObserver) |
| `total_mensajes` | INTEGER | Contador de mensajes en la conversación |
| `primer_mensaje_at` | DATETIME | Timestamp del primer mensaje |
| `ultimo_mensaje_at` | DATETIME | Timestamp del último mensaje |

### `mensaje`

Un registro por cada DM recibido.

| Columna | Tipo | Descripción |
|---------|------|-------------|
| `id_mensaje` | TEXT PK | `mid` de Meta (ID único del mensaje de Instagram) |
| `id_conversacion` | TEXT FK | Referencia a `conversacion` |
| `sender_id` | TEXT | ID del remitente |
| `es_entrante` | BOOLEAN | `1` si es del atacante, `0` si es respuesta del sistema |
| `texto` | TEXT | Contenido del mensaje |
| `urls_detectadas` | TEXT | JSON array de URLs encontradas en el mensaje |
| `timestamp_ig` | INTEGER | Epoch timestamp de Meta |

### `analisis_conversacion`

Un registro por cada análisis completado (puede haber múltiples por conversación).

| Columna | Tipo | Descripción |
|---------|------|-------------|
| `id_analisis` | INTEGER PK AUTOINCREMENT | |
| `score_urls` | REAL | Score del URLAnalyzer (0.0–1.0) |
| `score_texto` | REAL | Score del TextAnalyzer (0.0–1.0) |
| `score_ia` | REAL | Confidence del modelo IA (0.0–1.0) |
| `score_final` | REAL | `max(heuristic_score, ai_risk_score)` |
| `risk_level` | TEXT | LOW / MEDIUM / HIGH |
| `categoria_ataque` | TEXT | Categoría detectada por la IA |
| `tecnica_mitre` | TEXT | T1566.002 / T1566.003 / none |
| `principios_cialdini` | TEXT | JSON array de principios detectados |
| `etapa_lifecycle` | TEXT | approach / bond / hook / pressure / n/a |
| `explicacion_usuario` | TEXT | Explicación en español ≤280 chars |
| `explicacion_analista` | TEXT | Justificación técnica ≤500 chars |
| `respuesta_enviada` | INTEGER | `1` si ya se envió DM automático al atacante |

### `usuario_sistema`

Usuarios del dashboard web.

| Columna | Tipo | Descripción |
|---------|------|-------------|
| `username` | TEXT UNIQUE | Login del dashboard |
| `password_hash` | TEXT | Hash bcrypt |
| `ig_user_id` | TEXT | ID de Instagram de la cuenta monitoreada |
| `ig_username` | TEXT | Username de Instagram |
| `es_admin` | INTEGER | `1` → ve análisis pero NO el texto de mensajes |
| `es_cuenta_monitoreada` | INTEGER | `1` → usado por `es_cuenta_propia()` para anti-loop |
| `email` | TEXT | Para alertas por email |

## Funciones principales

### `save_message(sender_id, recipient_id, text, ...) → str`

Persiste un mensaje nuevo y actualiza/crea la fila en `conversacion`. Devuelve el `id_conversacion` calculado.

**ID de conversación:** `sha256(sorted([sender_id, recipient_id]).encode())[:16]` — bidireccional, da el mismo resultado independientemente del orden sender/recipient.

### `save_analysis_result(...) → int`

Inserta una fila en `analisis_conversacion` y actualiza `risk_level_actual` en `conversacion`. Devuelve el `id_analisis` generado.

### `get_conversation_history(id_conversacion, limit=50, exclude_message_id=None) → list[dict]`

Devuelve los últimos N mensajes de una conversación ordenados por `timestamp_ig`. Se usa para construir el historial que se pasa al modelo IA. El parámetro `exclude_message_id` evita incluir el mensaje actual (ya guardado) para no duplicarlo en el prompt.

### `get_conversation_info(id_conversacion) → dict`

Devuelve el estado actual de la conversación: `risk_level_actual`, `total_mensajes`, `participante_username`. El orchestrator lo usa al inicio del pipeline para leer el contexto previo.

### `update_username_if_missing(id_conversacion, participante_id, token) → str`

Consultala Graph API de Instagram para resolver el username del remitente. Solo actualiza la DB si `participante_username` está vacío. En caso de error devuelve el fallback `...{id[-8:]}` y lo persiste también (evita reintentar en cada mensaje).

### `es_cuenta_propia(sender_id) → bool`

Consulta `usuario_sistema` donde `es_cuenta_monitoreada = 1`. Usado por el webhook para detectar mensajes enviados por el propio sistema y evitar loops.

### `ya_fue_respondido(id_conversacion) → bool` / `marcar_respuesta_enviada(id_analisis)`

Implementan idempotencia para el DM automático: el atacante solo recibe una alerta aunque se detecten múltiples mensajes HIGH.

## Flujo de datos

```
webhook → save_message() → conversacion + mensaje
              │
orchestrator → save_analysis_result() → analisis_conversacion
              │
dashboard → get_conversation_history()
          → get_conversation_info()
          → [lee todas las tablas via JOINs inline]
```

## Índices definidos

```sql
idx_mensaje_conversacion    ON mensaje(id_conversacion)
idx_analisis_conversacion   ON analisis_conversacion(id_conversacion)
idx_analisis_risk           ON analisis_conversacion(risk_level)
idx_conversacion_risk       ON conversacion(risk_level_actual)
```

Los índices optimizan las queries más frecuentes del dashboard: filtrar conversaciones por riesgo y leer el historial de mensajes de una conversación.

## Decisiones de diseño

**SQL crudo sin ORM**: las queries son específicas y conocidas — no hay queries dinámicas que justifiquen el overhead de un ORM. `aiosqlite` es suficiente para el volumen del TIF. Ver `decisiones_tecnicas.md` #6.

**ID bidireccional con SHA-256**: `sha256(sorted([A, B]))[:16]` da el mismo ID independientemente de quién sea sender y quién recipient. Crítico para importar conversaciones históricas donde el orden puede variar.

**Sin Supabase**: el diseño inicial usaba Supabase como backend de datos. El tutor indicó migrar a SQLite a mitad del proyecto. `supabase_client.py` fue eliminado en commit `868042a`. Ver `decisiones_tecnicas.md` #9.
